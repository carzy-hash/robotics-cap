Code as Runtime · Runtime Trace RL · 03

Roll out inside the runtime.
Run RL over the complete trace.

The RL object in Code as Runtime is neither a single action nor text detached from execution. It is an executable trajectory jointly produced by the main Agent and runtime: read an observation, choose a decision, write code, call tools, modify the Action Queue, check results, and recover from failure. It draws on executable code-agent traces[3]; CaP-X further demonstrates multi-turn feedback and verifiable-reward RL for embodied coding agents[8]. Building on them, this article discusses outcome, progress, constraint, and cost signals for the full runtime trace.

01 · Optimization object

The training object is an executable trace,
not only the final action segment.

It resembles the training loop of an executable Code Agent: the model autoregressively writes the next runtime decision, the environment executes code, tools, and actions, and a new observation returns to context. This interleaved reasoning / acting form goes back to ReAct[2]. RL optimizes the closed-loop policy across multiple turns, not merely whether the final action happens to succeed.

WHAT IS AUTOREGRESSIVE

The complete high-level policy interface

Every turn extends the existing trace: observation requests, code, tool results, queue decisions, self-checks, and recovery choices all condition the next token.

WHAT IS NOT IMPLIED

No token-by-token motor control

Action Chunks can still come from ACT-like policies[4], π₀-like flow policies[5], planners, or interpolators. The autoregressive object is the upper-level runtime trace.

FAIR VLA COMPARISON

The difference is the primary supervision outlet

VLAs such as RT-2 can also produce action tokens autoregressively[13]. The actual distinction is that Code as Runtime makes the executable policy process itself the primary generation and RL object instead of assigning reward only to action sequences.

02 · Verifiers and credit

Final success gives direction.
Process rewards assign credit.

A single success reward is too sparse and can encourage simulation shortcuts. A better design preserves an independent outcome verifier while using checkers of varying reliability to describe progress, constraints, calls, and recovery quality.

R(trace)=outcome+Δ progress+endpoint checks−violations−runtime cost
SignalWhat it supervisesPreferred evidenceMain risk
OutcomeWhether the task is ultimately completedSimulation state / real sensors / human reviewSparse; may hide a wrong process
ProgressWhether distance to a subgoal truly shrinksPotential difference, stage conditions, geometryProxy hacking
EndpointGoal, observation, constraint, call, state, recoveryRules, physics, calibrated visual verifiersA bad checker corrupts credit
SafetyCollision, excessive force, boundaries, permissionsDeterministic rules and an independent safety systemMust not be overridden by self-evaluation
CostUseless observations, verbose code, frequent queue editsToken, latency, call, and execution countsToo much pressure suppresses necessary recovery
A progress reward should describe a state change, not reward the Agent for saying it made progress.

For example, reward the potential difference from the gripper to a reachable pre-grasp, the geometric change as an object enters the target region, or a calibrated contact-state change. A natural-language self-check is only a claim to verify; it cannot grade itself.

03 · Rollout and optimization loop

Every RL turn must execute,
not merely receive a text critique.

A training turn starts from a replayable runtime state, samples an Agent decision, executes it to produce a real observation, and lets independent verifiers write back rewards and failure endpoints. SFT and privileged solvers provide only the initial state distribution; the main data should gradually shift toward on-policy rollouts.

04 · Cold start: privileged projection

Ground truth may help solve the task.
Its source must never be fabricated.

Before the policy can roll out reliably, simulation ground truth can provide feasible solutions and checking labels for a cold start ahead of RL. But a trace that claims the vision system derived an exact value it never observed creates an undeployable causal shortcut. The right goal is deployment-shaped initialization, not long-term replacement of on-policy exploration by an oracle.

PRIVILEGED ORACLE

Solve a grasp from mesh ground truth

mesh_gt = sim.object_mesh(id)
pose_gt = sim.object_pose(id)
g_star = antipodal_grasp(mesh_gt, pose_gt)
execute(g_star)

It answers “what feasible solution exists” and supplies collision, contact, and terminal-success labels.

→
DEPLOYMENT-SHAPED TRACE

Produce candidates from visual representations

mesh_hat = reconstruct(multiview_rgbd)
g_vis = propose_grasp(mesh_hat)
residual = refine_grasp(obs, g_vis)
queue.push(grasp_chunk(g_vis + residual))

The main Agent calls only perception and refinement helpers available at deployment.

→
TEACHER RESIDUAL

Use the Magic Offset only as scaffolding

delta_magic = g_star - g_vis
label(refine_grasp, delta_magic)
record(privileged=true,
       residual=delta_magic,
       projection_error=...)

The offset trains a deployable residual helper and is annealed to zero through the curriculum. It must not masquerade as a visual observation.

Policy inputContains only observations, states, and APIs shared by simulation and reality.
Teacher sidecarStores ground truth, Magic Offset, oracle actions, failure causes, and label confidence separately.
Acceptance conditionRemove the sidecar and roll out again; advance only when the observation-only policy still passes the verifier.

The same projection method extends to more tasks

PLACEMENTStable placement

Ground-truth support surfaces and stable poses produce oracle goals; visual scene reconstruction produces candidates, and a residual teacher supervises final pose refinement.

ARTICULATIONDoors and drawers

Ground-truth joint axes and contact points produce feasible trajectories; the student estimates joint state from vision and force and learns when to update a force handler.

OCCLUSIONActive observation

A ground-truth visibility graph selects the best camera view; the projected trace instead calls for viewpoint changes and multi-frame fusion from uncertainty.

RECOVERYFailure recovery

Simulation directly provides slip, collision, or missed-grasp causes; the student sees only observable symptoms and learns to reobserve, retract, or stop.

05 · Runtime action space

RL explores not only what to do,
but also how the runtime should be written.

The same task can admit multiple correct Action outputs and handler implementations. A rollout can sample candidate code, execute unit tests, inject anomalies, and let verifiers compare success, recoverability, and runtime cost, preventing the main Agent from being locked into one rigid template.

ACTION BUILDER CANDIDATES

Normal task actions

# equivalent valid implementations
queue.push(interpolate(keyframes))
queue.push(plan_to_pose(goal))
queue.push(vla_primitive(goal, horizon=.8))

Under the same typed action contract, cover interpolation, motion planning, learned primitives, and different queue mutations.

HANDLER CANDIDATES

Events and fast responses

@on_force(threshold=12.0)
def guard(obs, queue):
    queue.truncate(after="inflight")
    queue.push(stabilize(obs))
    emit_event("force-guard")

Cover on-frame, force, tactile, timeout, and tracker-loss handlers while supervising triggers, state lifetime, queue permissions, and exit conditions.

normal rollout→inject slip / occlusion / delay→handler fires→queue mutation→verifier grades recovery
Full capability does not mean a handler should be written every time.

Training must include negative examples: do not install a handler when no low-latency response is needed; remove an expired handler; leave the queue alone when a simple CONTINUE is enough. Otherwise, the model will hide uncertainty behind an increasingly complex runtime.

06 · CAP-derived curriculum

Inject faults at every supervised endpoint
so recovery becomes routine training data.

The direct lesson from CaP-X / CaP-RL is that embodied coding agents can improve under execution feedback and verifiable rewards[8]. Code as Runtime further treats goals, observations, constraints, calls, states, and recovery in the explicit trace as fault-injection endpoints instead of merely adding more successful demonstrations.

01Goal

Replace similar objects, swap instructions, add distractors.

02Observation

Occlusion, blur, camera mismatch, missing depth.

03Constraint

Change exclusion zones, payload, speed, and force limits.

04Call

Wrong units, unreachable poses, timeouts, tool failures.

05State

Slips, collisions, missed grasps, latency, partial execution.

06Recovery

Compare continue, retry, change viewpoint, degrade, and stop.

SHARED APISimulation and reality share a typed action contract

Parameters, units, coordinate frames, timeouts, failure codes, and cancellation semantics remain identical; only the execution backend changes.

TRUST LEVELRecord verifier type and confidence

Rules, simulation physics, real sensors, vision models, and model self-evaluation cannot be treated as equally reliable labels.

SHORTCUT AUDITSearch explicitly for simulator exploitation

Separate scenes, meshes, random seeds, and task templates; check whether a trace reads fields unavailable in deployment.

07 · RL acceptance conditions

RL works only if the policy
improves during execution.

The primary acceptance target is on-policy performance of the observation-only policy, not teacher rollouts or offline token loss. Along with terminal success, verifier calibration, recovery coverage, policy entropy, runtime cost, and real-robot transfer must improve together.

Privileged gapDoes the gap between oracle success and observation-only success keep shrinking?
Intervention rateDoes reliance on Magic Offset, ground-truth recovery, or teacher patches decline?
Verifier calibrationDo process rewards predict final success instead of merely rewarding an elegant trace?
Recovery coverageUnder unseen perturbations, can the Agent locate the failure endpoint and choose an appropriate recovery?
Runtime economyAt equal success, does it use fewer useless tokens, helper calls, and handlers?
Real-robot transferAfter sharing the interface, how much perception, contact, latency, and calibration gap remains?

The core of this RL route is to have the Agent continually produce, execute, and revise traces inside a deployment-shaped runtime, then use calibrated verifiers to attribute environmental consequences to specific decisions. Teachers, simulation ground truth, and Magic Offset are only scaffolding into this loop. The policy actually optimized and ultimately deployed is an on-policy Agent that depends only on visible observations and callable runtime APIs.
