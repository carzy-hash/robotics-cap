Code as Runtime · 运行时轨迹 RL · 概念版 v0.1 · 未经同行评审

用执行后果，
训练每一次决策。

如果奖励只落在最终动作上，更早的观测、代码修改、队列更新、事件处理器和恢复决策就只能得到很弱的信用分配信号。Code as Runtime 提议在完整执行轨迹上训练上层 Agent，并结合最终结果与经过验证的进度、约束、有效性、恢复和成本信号。底层 Action Chunk 仍可由现有控制器生成。本文给出训练设计，不报告已经完成的 RL 实验或性能增益。

CodeAct[3]为可执行代码 Agent 轨迹提供启发。CaP-X[8]报告了其具身 coding-Agent 设置中的多轮反馈与可验证奖励 RL；这些方法能否扩展到 Code as Runtime 尚未验证。

01 · 优化对象

优化产生执行轨迹的
每一次决策。

它更像可执行代码 Agent 的训练闭环：模型自回归写出下一次运行时决策，环境执行代码、工具与动作，再把新的观测放回上下文。这种推理与行动交错的形式可追溯到 ReAct[2]；RL 优化的是这条跨越多轮的闭环策略，而不只是最终动作是否碰巧成功。

自回归对象

整个主策略接口

每一轮输出都接在已有轨迹后面：观察请求、代码、工具结果、队列决策、自检与恢复选择都会影响后续词元。

不代表什么

不要求逐词元控制电机

Action Chunk 仍可由 ACT 类策略[4]、π₀ 类流策略[5]、规划器或插值器生成；自回归对象是上层运行时轨迹。

与 VLA 的公平对比

区别在主要监督目标

RT-2 等 VLA 也可以自回归地产生动作词元[13]。这里真正不同的是：Code as Runtime 把可执行策略过程本身作为主要生成与 RL 对象，而不是只把奖励落在动作序列上。

02 · 运行时动作空间

RL 同时选择动作
和运行时代码。

同一任务可以有多种正确的 Action 输出和处理器实现。执行采样可以生成候选代码、运行单元测试并注入异常，再由验证器比较成功率、恢复能力和运行成本，避免主 Agent 被固定在一种僵硬模板里。

动作构建器候选

正常任务动作

# equivalent validated requests
candidates = [
  QueueUpdate.append(interpolate(keyframes)),
  QueueUpdate.append(plan_to_pose(goal)),
  QueueUpdate.append(vla_primitive(goal, horizon=.8))
]

在相同的类型化动作契约下，覆盖插值、运动规划、学习得到的动作原语和不同队列更新。

事件处理器候选

事件与快速响应

@on_force(threshold=12.0, scope="transport", expires="release")
def guard(obs):
    emit_event("force-guard")
    return QueueUpdate.replace(stabilize(obs), reason="force-guard")

覆盖逐帧、力、触觉、超时和跟踪丢失事件；同时监督触发条件、状态寿命、队列权限和退出条件。

常规执行采样→注入滑落、遮挡或延迟→事件处理器触发→队列更新→验证器评估恢复
不要把安装事件处理器训练成默认动作。

训练中要同时加入负例：没有低延迟需求时不安装事件处理器；事件处理器过期后主动移除；简单的 CONTINUE 足够时不改队列。否则模型会通过增加不必要的运行时代码来回避不确定性。

04 · 验证器与信用分配

结合最终成功
和经过验证的过程信号。

保留独立的结果验证器，再加入进度、约束、调用和恢复检查器，并记录每个检查器的可靠性。

R(trace)=outcome+Δ progress+endpoint checks−violations−runtime cost
信号监督什么优先证据主要风险
结果任务最终是否完成仿真状态 / 真机传感器 / 人工复核稀疏，可能掩盖错误过程
进度距离子目标是否真实缩短势函数差、阶段条件、几何量被代理指标劫持
端点目标、观察、约束、调用、状态、恢复规则、物理、校准后的视觉验证器错误检查器污染信用分配
安全碰撞、超力、越界和权限确定性规则与独立安全系统不得由模型自评覆盖
成本无效观察、冗长代码、频繁修改队列词元、延迟、调用和执行计数过强会压制必要恢复
进度奖励应描述状态变化，而不是奖励“说自己取得了进展”。

例如奖励夹爪到可达预抓取位姿的势函数差值、物体进入目标区域的几何变化，或经过校准的接触状态变化；自然语言自检只能作为待验证声明，不能自己给自己打分。

05 · 基于 CAP 的课程

在每个已纳入监督的检查点注错，
让恢复成为常规训练数据。

CaP-X / CaP-RL 的直接启发是：具身代码 Agent 可以在执行反馈与可验证奖励下改进[8]。Code as Runtime 进一步把显式轨迹中的目标、观察、约束、调用、状态和恢复作为可注错端点，而不是只增加成功示范数量。

01目标

替换相似物体、交换指令、加入 distractor。

02观察

遮挡、模糊、相机失配、深度缺失。

03约束

改变禁入区、负载、速度与力上限。

04调用

单位错误、不可达 pose、timeout、工具失败。

05状态

滑落、碰撞、抓空、延迟与部分执行。

06恢复

比较继续、重试、换视角、降级与停止。

共享 API仿真与真机共享 typed action contract

参数、单位、坐标系、timeout、失败码和取消语义保持一致，只替换执行后端。

可信度等级记录 verifier 类型与置信度

规则、仿真物理、真机传感器、视觉模型和模型自评不能被当成同等可靠标签。

捷径审计专门寻找 simulator exploitation

隔离场景、mesh、随机种子与任务模板；检查 trace 是否读取了部署时不存在的字段。

06 · RL 验收条件

用仅依赖观测的
在线策略轨迹验收策略。

报告最终成功率、验证器校准、恢复覆盖、策略熵、运行时成本和真机迁移，不得用教师策略成功率或离线词元损失代替。

特权信息差距特权策略和仅依赖观测的策略之间，成功率差距是否持续缩小？
干预率需要 Magic Offset、真值恢复或教师补丁的比例是否下降？
验证器校准过程奖励是否真的预测最终成功，而非只奖励漂亮轨迹？
恢复覆盖率未见扰动下，Agent 是否能定位失败端点并选择合适恢复？
运行时开销成功率相同时，是否减少无效词元、辅助函数调用和处理器数量？
真机迁移共享接口之后，感知、接触、延迟和标定仍有多大差距？

通过预期用于部署的同一套运行时接口执行每次 Agent 决策，再根据执行后的状态变化分配奖励。教师数据和仿真真值可以用于初始化，但通过验收的策略只能依赖可见观测和可调用的运行时 API。
