Agent 每次唤醒都要同时接收固定策略、缓慢变化的历史，以及频繁变化的运行时和传感器状态。如果易变内容出现得太早，严格的前缀缓存就必须重算其后的所有内容。本文提出按稳定性排列每轮输入：固定契约在前，当前运行时状态随后，最新图像最后。这是一项设计假设；图像词元的缓存命中率和延迟收益仍需在目标推理栈上实测。

ReAct[2] 与 CodeAct[3]提供交错式动作、观察和执行历史基础，但没有验证本文提出的排序。

01 · 唤醒时的完整上下文

用八个有序区块，
组装每一轮上下文。

这里假设推理服务对多模态输入使用严格的前缀缓存；SGLang 的 RadixAttention 是这类跨请求 KV 缓存复用的代表实现[7]。只有从开头开始完全一致的词元与图像内容才能复用；任何过早出现的时间戳、队列余量或新图像，都会让后续内容失去缓存机会。目标服务是否缓存图像词元，仍需用实际缓存命中率验证。

02 · 缓存从哪里失效

缓存只复用一条
精确的公共前缀。

第 N+1 轮能复用多少，取决于它与第 N 轮从开头起保持一致到哪里。最早发生变化的位置决定本轮缓存从哪里开始失效。

03 · 粘性指数历史

指数衰减负责覆盖时间，
粘性槽位负责保住缓存。

历史采样维护一组持久槽位：新帧只进入最近端；较老槽位在跨过时间桶边界或出现重要事件时替换。这样可以同时覆盖长时间跨度并保持公共前缀。

01

旧到新排列相同的旧图像形成最长公共前缀；最近槽位的轮换只影响后缀。

02

槽位按事件更新时间桶跨界、锚点触发或预算压缩时，才替换对应图像标识。

03

图像与说明一起冻结时间戳、相机标识、说明文字与图像必须作为一个不可变单元，否则文字变化同样会使缓存从该位置起失效。

04

按信息增益淘汰先删除与邻近帧重复的普通图像，保留动作转折、接触和失败证据。

06 · 上下文构建器契约

真正需要实现的，
是确定性的上下文构建器。

缓存收益最终取决于序列化是否稳定。相同状态必须生成相同前缀；预算不足时也要使用明确、可回放的淘汰顺序。

当前时间归入当前轮。时间戳、请求标识和动态统计统一排列在系统与辅助函数区之后。

所有集合稳定排序。动作原语、处理器、对象状态估计和工具结果使用确定的键；禁止依赖映射的偶然遍历顺序。

历史使用不可变图像单元。图像标识、说明文字、相机和时间一旦进入槽位就一起冻结，直到该槽位被明确替换。

超预算时按价值淘汰。先压缩重复标准输出与普通帧，再缩短决策轨迹；固定保留安全契约、当前代码、队列状态和最新图像。

记录缓存版本链。每轮轨迹保存前缀版本、首个变化区块、实际词元占比与缓存命中率，以便测量缓存复用率及其带来的计算量和延迟收益。

def build_agent_context(snapshot, episode, budget):
    blocks = [
        SYSTEM_POLICY_V3,
        PRIMITIVES_AND_HELPERS_V8,       # immutable, versioned
        episode.frozen_contract(),       # stable inside this episode
    ]

    blocks += episode.history.select_sticky(
        buckets=[64, 32, 16, 8, 4, 2, 1],
        keep_event_anchors=True,
        order="oldest_first",
        budget=budget.history,
    )

    blocks += [
        stable_serialize(snapshot.runtime),
        summarize_recent_delta(snapshot, turns=4),
        current_sensor_summary(snapshot),
        DECISION_REQUEST,
        snapshot.latest_image,          # always the last content block
    ]

    assert blocks[-1].type == "image"
    return blocks
