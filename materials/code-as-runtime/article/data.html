Code as Runtime · Real-data Trace SFT · Concept v0.1 · Not peer reviewed

Project continuous recordings
into causal runtime turns.

Real-robot demonstrations record continuous sensor and action streams, not the causal turn-level decisions that Code as Runtime must learn. Naive slicing can leak future frames, ignore inference latency, or rewrite actions that the robot has already executed. We propose replaying each episode on a calibrated timeline and projecting it into context → decision pairs with explicit queue state, source provenance, and replay checks. The projected dataset and a trained policy have not been evaluated.

DROID[10] and Open X-Embodiment[11] provide real-robot trajectories and standardized formats. Neither validates this projector.

01 · SFT projection objective

Keep raw records separate
from projected turns.

Raw recordings are fixed evidence. Building an SFT example requires explicit choices about Agent wake time, inference latency, visible observations, queue state, and target decision. The projector must record those choices and must never copy future information into policy input.

Projection does not rewrite facts.

The same raw episode can yield multiple decision timings or code expressions, but every synthesized field must retain its source, method, and confidence. Anything from a future frame, human correction, or simulation ground truth belongs only in the teacher sidecar and must never masquerade as policy input.

02 · Canonical event ledger

Align every stream
on one episode clock.

Video frames, control commands, actual robot motion, and contact feedback do not arrive simultaneously. Open X-Embodiment demonstrates the importance of a unified format across embodiments[11]. Here, each stream must also preserve its source timestamp before establishing a calibrated episode clock; otherwise, a seemingly plausible turn may already use an image that had not yet arrived.

03 · Pseudo-time replay

The robot does not stop
while the model is inferring.

Synchronous slicing creates a world that never existed: the Agent sees the final result of an action segment before deciding how that segment should be written. RTC explicitly models that an old chunk keeps executing during model inference and that the executed prefix is frozen under asynchronous constraints[6]. VLA-Corrector studies shortening the execution horizon after detecting deviation[12]. Accordingly, this article performs pseudo-time replay along the demonstration trajectory.

01Select wake points

Mix a fixed stride, stage events, and anomaly events. Do not wake only when the correct answer is obvious.

02Sample inference latency

Sample d from the target model's latency distribution instead of assuming an instantaneous decision.

03Freeze the executed prefix

Actions sent or executed during inference cannot be recalled; only the remaining queue tail can be replaced.

04Randomize truncation timing

Mix truncations before, at, and after deviations so the policy does not learn only one timing pattern.

04 · From motion to runtime decisions

Keep direct Action Chunks
when code fails replay.

Demo2Code explores two-stage synthesis from demonstration summaries to executable robot code[9]. Here, dense actions are first segmented by contact, curvature, speed, and task stage, then reconstructed with restricted primitives. Low-curvature, non-contact segments are often suitable for compression into code; contact-rich or poorly fitted segments remain ACT-like Action Chunks[4]. Convert only when conversion works: retain a real chunk rather than manufacture elegant but incorrect code.

05 · Proposed minimum trace shape

One episode trace yields
many SFT examples.

Each turn uses context available before available_until as input and records when the decision takes effect. Queue snapshots at wake, commit, and after-update preserve what became irrevocable during inference. Tool results and executor events enter the next context. This is a proposed minimum shape, not a stable schema.

Re-expand every code-built chunk and compare it with the actual trajectory. Check that every queue mutation preserves the executed prefix. Verify that every CONTINUE leaves enough queue to reach the next turn. Turns that fail these checks do not enter the high-confidence SFT set.

07 · Filtering and acceptance

Before data can train,
it must pass a causal audit.

A successful episode is not automatically good data. The real danger is a trace that succeeds for the wrong reason: it uses future frames, leaks ground truth, attributes human takeover to the Agent, or explains actions with code that cannot replay. Filters must find these shortcuts before training.

Temporal leakageDoes any context reference occur after available_until?
Replay equivalenceIs the error between expanded code and the recorded trajectory below the segment threshold?
Queue validityDid any mutation alter an executed or in-flight, irrevocable prefix?
Privilege leakageDid ground truth, human corrections, or after-frames enter policy input?
Intervention attributionWas the trace split around human takeover with control ownership marked?
Failure valueDoes a failure include a localized endpoint and later recovery, rather than only terminal failure?
Media integrityDo all external images, sensor windows, and chunk references exist and decode?
Projection confidenceAre low-confidence synthesized fields downweighted, reviewed, or excluded from SFT?

The proposed pipeline should produce multi-turn SFT in which every input was available at that turn and every target is the next executable Agent decision. RL may reuse the same trace shape. For SFT, replay each turn and confirm that its context, queue state, and target match the recorded episode. Causal visibility and replay fidelity remain evaluation targets, not established results.
