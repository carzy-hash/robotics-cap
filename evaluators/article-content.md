# Article content evaluator

## 目标

判断读者是否能正确理解文章提出的问题、核心设计、适用边界和未验证部分。这个 evaluator 检查文字与论证，不检查引用是否真实，也不检查 Pages 配置。

## 输入

读取以下内容：

- 目标文章的公开页面及对应语言版本。
- 对应的 `brief.md`、`outline.md` 和 `decision.md`。
- 系列首页、导航文字和仓库 `README.md` 中对文章的描述。
- 本次改动的 diff。

如果同一主张出现在多个页面，检查各处是否使用同一个名称和同一证据强度。

## 阻塞条件

出现以下任一情况时返回 `FAIL`：

- 标题、摘要或开场把概念设计写成已经验证的方法。
- 开场没有说明 Code as Runtime 解决什么问题，读者必须先理解内部术语才能知道文章在讲什么。
- 文章把高层 Agent、event handler、Action Queue 和低层控制器的职责混在一起。
- 正文的核心结论与 `brief.md` 的范围或 `decision.md` 的 canonical 决策冲突。
- 中文版与英文版对同一核心主张给出不同含义。
- 文章声称一种方法优于另一种方法，却没有在同一段说明比较对象和证据范围。

## 评分

总分为 100 分。

### 定位与开场，20 分

检查以下问题：

- 第一屏是否说明问题、设计和研究状态。
- 仓库描述是否区分研究札记、实现仓库和实验结果。
- 标题是否准确，不依赖夸张词或没有定义的缩写。
- 摘要是否能独立回答“它是什么”和“为什么需要它”。

### 读者与术语，15 分

检查以下问题：

- 文章是否符合 `brief.md` 指定的读者背景。
- CAP、Code as Runtime、Agent、handler、Action Queue 和 Runtime Trace 是否在首次使用时定义。
- 同一概念是否在所有文章中保持同一个名称。
- 中英文版本是否保留技术含义，而不是逐句硬译。

### 论证顺序，25 分

检查以下问题：

- 每一节是否承担一个明确任务。
- 论证是否从问题进入机制，再进入例子、边界和验证计划。
- 香蕉任务或其他例子是否证明一个明确机制，而不是替代证据。
- 段落是否区分已有工作、本文设计和待验证假设。
- 长文是否提供目录、阅读路径和前后篇导航。

### 系统边界，20 分

检查以下问题：

- 主 Agent、runtime、handler、Action Queue、action builder 和安全控制器是否各有一个明确责任。
- 正文是否说明代码能修改什么，不能绕过什么。
- 文章是否避免暗示语言模型直接承担高频电机控制。
- 与 Code as Policies、CaP-X、RTC、VLA 和 Action Chunk 的关系是否清楚。

### 文字质量，20 分

检查以下问题：

- 每个句子是否只承担一个主要意思。
- 是否删除空话、宣传词、重复总结和没有来源的笼统判断。
- 图题、标签、表格标题和正文是否使用同一套术语。
- 数字与具体工具是否标明 `Illustrative`、`Measured` 或 `Required`。
- 读者能否在第一次阅读时分辨机制、例子和结论。

## 评审步骤

1. 只读标题、状态标签、摘要和第一张图。用两句话复述文章。如果无法复述，记录开场问题。
2. 对照 `brief.md`，列出核心主张、目标读者和范围。检查公开页面是否保持一致。
3. 为每一节写一句“本节负责什么”。两节职责重复时，要求合并或重写边界。
4. 标出所有比较句、数字、工具名和结果性动词。检查它们是否说明证据强度。
5. 对照中英文页面的标题、摘要、关键定义和结论。技术词可以保留英文，但含义不能漂移。
6. 按 `evaluators/README.md` 的格式输出结论。

## 输出要求

除共同输出外，增加以下内容：

```markdown
## Reader reconstruction

- Problem: <the problem a reader will infer>
- Proposal: <the design a reader will infer>
- Boundary: <what the design does not own>
- Evidence status: <what the reader will believe has been verified>
```

这四项必须基于公开页面，而不是基于 evaluator 已经读过的内部 brief。如果公开页面传达了错误信息，把差异记录为 finding。
